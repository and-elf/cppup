# cppup Configuration API

The configuration API is the C++ surface a user's `build.cpp` calls
into. It defines what a project depends on, how it should be compiled,
which binaries / libraries / tests it produces, and how it adapts to
the resolved toolchain, profile, platform, and feature flags.

`build.cpp` exports a single function:

```cpp
extern "C" cppup::configuration::BuildConfiguration configure();
```

The cppup CLI compiles `build.cpp` into a shared object, `dlopen`s it,
calls `configure()`, and drives the rest of the build from the returned
value.

## Including the API

User projects include one header:

```cpp
#include <cppup/configuration.hpp>
using namespace cppup::configuration;
```

[`include/cppup/configuration.hpp`](../../../include/cppup/configuration.hpp)
is an amalgamated header generated by
[`scripts/amalgamate_configuration_header.sh`](../../../scripts/amalgamate_configuration_header.sh)
and embedded into the cppup binary at build time (as a generated
comma-separated byte list `#include`d into an array — portable to compilers
without `#embed`). Projects pick it up automatically, so no library link step
or `find_package(cppup_config)` is required — the header travels with cppup.

The implementation is split across this directory:

```
src/core/configuration/
├── build_configuration.hpp   # struct BuildConfiguration
├── types.hpp                 # Package / Module / Toolchain / Flag / Definition / TestFramework
├── outputs.hpp               # Binary / Library / Test / BuildStep
├── profile.hpp               # Profile + ProfileProcessor
├── platform.hpp              # compile-time when_windows / when_linux / when_macos / when_x86_64 / when_arm64
├── runtime.hpp               # when_toolchain / when_profile / when_feature / when_env*
├── cppup_config.hpp          # legacy convenience helpers (warnings::, optimization::, debug_profile() …)
└── toolchain_flags.hpp       # CxxStandard / WarningLevel expansion per compiler family
```

## `BuildConfiguration` shape

```cpp
struct BuildConfiguration {
  std::optional<Toolchain>    toolchain;
  std::vector<Package>        packages;
  std::vector<Module>         modules;

  std::vector<std::string>    sources;
  std::vector<Flag>           compile_flags;
  std::vector<Flag>           link_flags;
  std::vector<std::string>    include_paths;
  std::vector<Definition>     definitions;

  std::vector<Binary>         binaries;
  std::vector<Library>        libraries;
  std::vector<Test>           tests;
  std::vector<TestFramework>  test_frameworks;

  std::vector<Subproject>     subprojects;
  std::vector<Profile>        profiles;
  std::vector<BuildStep>      build_steps;

  // Filled by the host before configure() runs:
  std::string                        target_os;
  std::string                        target_arch;
  std::map<std::string, std::string> environment;
  std::set<std::string>              features;
};
```

### Core inputs

| Field | Purpose |
|---|---|
| `toolchain` | Compiler name + dialect/warnings policy. `Toolchain::cxx_standard` and `Toolchain::warnings` are strong enums (`CxxStandard::{Cxx17,Cxx20,Cxx23,Cxx26}`, `WarningLevel::{None,Standard,Strict,Werror}`); `Toolchain::extra_flags` is the escape hatch for verbatim compiler-specific flags. The expansion to family-specific flags (gcc/clang `-std=…`, MSVC `/std:…`) lives in [toolchain_flags.hpp](toolchain_flags.hpp). |
| `packages` | External dependencies. See [docs/packages.md](../../../docs/packages.md) and the `from_*` helpers in `types.hpp`. |
| `modules` | First-class C++ modules. |
| `sources`, `compile_flags`, `link_flags`, `include_paths`, `definitions` | Project-wide values applied to every target. |

### Outputs

| Field | Purpose |
|---|---|
| `binaries` | `Binary{.name, .sources, …}` — executables. |
| `libraries` | `Library{.name, .sources, .type = LibraryType::Static \| Shared}`. |
| `tests` | `Test{.name, .sources, .framework = "gtest"}` — `.framework` selects which `TestFramework` to link against. |
| `test_frameworks` | Registered framework integrations (gtest is built in). When a `TestFramework` has no explicit `.package`, the framework plugin's `default_package()` is used and recorded in `cppup.lock`. |
| `build_steps` | Custom steps with declared dependencies, executed in order before/after the main build. |
| `subprojects` | Nested projects whose libraries/binaries get merged into this build. Backend (cppup / CMake / Make / header-only) is inferred from directory contents and can be overridden. |

### Profiles

```cpp
config.profiles = {
    Profile{.name = "debug",
            .compile_flags = {Flag{"-O0"}, Flag{"-g"}},
            .definitions   = {Definition{"DEBUG", "1"}}},
    Profile{.name = "release",
            .compile_flags = {Flag{"-O3"}},
            .definitions   = {Definition{"NDEBUG"}}},
};
```

Active profile is selected by `cppup build --profile X` or persisted
via `cppup profile select X` to `cppup.lock`. The CLI exports it as
`CPPUP_ACTIVE_PROFILE` before compiling `build.cpp` so `when_profile`
can branch on it from inside `configure()`. Selection precedence and
selection mechanics live in [docs/packages.md](../../../docs/packages.md).

### Platform queries

`target_os`, `target_arch`, `environment`, and `features` are populated
by the host before `configure()` runs. Read them with:

- `has_feature(config, "gui")`, `has_all_features(config, range)`,
  `has_any_feature(config, range)`
- `get_env(config, "VAR")`, `get_env_or(config, "VAR", "default")`

…or use the matching `when_*` helpers below.

## `when_*` helpers

The `when_*` helpers turn conditional configuration into linear,
imperative code in `configure()`. They come in two families:

### Compile-time (host of `build.cpp` itself)

In [`platform.hpp`](platform.hpp). These are `if constexpr` wrappers
around `#ifdef` — the branch the host *compiled* `build.cpp` on. The
non-matching branch is dead code at the user's compile time.

| Helper | Fires when |
|---|---|
| `when_windows(fn)` | `_WIN32` defined when `build.cpp` was compiled |
| `when_linux(fn)`   | `__linux__` defined |
| `when_macos(fn)`   | `__APPLE__` defined |
| `when_x86_64(fn)`  | `__x86_64__` / `_M_X64` |
| `when_arm64(fn)`   | `__aarch64__` / `_M_ARM64` |

Use these for *host* platform — code paths that only make sense to
emit on a particular OS or arch. Target-arch concerns belong in
`when_toolchain` (the toolchain name carries the target triple).

```cpp
when_linux([&] {
  config.link_flags.push_back(Flag{"-pthread"});
});
when_arm64([&] {
  config.compile_flags.push_back(Flag{"-march=armv8-a"});
});
```

### Runtime (host-resolved selection and config state)

In [`runtime.hpp`](runtime.hpp). These read state the cppup CLI
populated *before* `configure()` ran — either via process env vars
(`CPPUP_ACTIVE_TOOLCHAIN`, `CPPUP_ACTIVE_PROFILE`) or via
`BuildConfiguration::features` / `BuildConfiguration::environment`.

| Helper | Fires when | Reads |
|---|---|---|
| `when_toolchain(name, fn)` | active toolchain matches `name` | `CPPUP_ACTIVE_TOOLCHAIN` |
| `when_profile(name, fn)`   | active profile matches `name`   | `CPPUP_ACTIVE_PROFILE` |
| `when_feature(config, name, fn)` | `config.features` contains `name` | `BuildConfiguration::features` |
| `when_env(config, var, value, fn)` | `config.environment[var] == value` | `BuildConfiguration::environment` |
| `when_env_exists(config, var, fn)` | `config.environment` contains `var` | `BuildConfiguration::environment` |

`when_toolchain` / `when_profile` are early-binding: the CLI resolves
selection (CLI flag > `cppup.lock` > `$CXX`/`$CC` > default) **before**
compiling `build.cpp`, so inside `configure()` you can confidently
customize `config.toolchain` / flags based on what's about to drive
the build.

`when_profile` does not match an empty active profile — write a
separate unguarded block if you need a "no profile" default.

```cpp
when_toolchain("clang++", [&] {
  config.compile_flags.push_back(Flag{"-stdlib=libc++"});
});
when_profile("release", [&] {
  config.compile_flags.push_back(Flag{"-flto"});
});
when_feature(config, "gui", [&] {
  config.packages.push_back(from_git("qt6", "https://github.com/qt/qt6.git", "6.7.0"));
});
when_env_exists(config, "CI", [&] {
  config.compile_flags.push_back(Flag{"-Werror"});
});
```

### Direct accessors

When you need the value rather than the branch:

```cpp
std::string_view tc = active_toolchain();   // "" if unset
std::string_view pr = active_profile();     // "" if unset
```

## Package helpers

`config.packages` accepts `Package` values; the `package_helpers`
namespace exposes shorthand constructors that match the source kinds:

```cpp
using namespace cppup::configuration::package_helpers;

config.packages = {
    from_git      ("fmt",   "https://github.com/fmtlib/fmt.git", "10.2.1",
                            /*dependencies=*/ {from_git("zlib", "https://github.com/madler/zlib.git")}),
    from_directory("mylib", "../mylib"),
    from_registry ("boost", "1.84.0"),     // stub today
    from_tar      ("ext",   "https://.../ext.tar.gz"),
    from_zip      ("snap",  "https://.../snap.zip"),
    from_http     ("blob",  "https://.../blob"),
};
```

Every `from_*` helper takes a final `dependencies` parameter listing
direct children. The manifest *is* the dependency graph — there is no
central registry that knows what fmt depends on. `cppup lock` walks
`config.packages` plus each `PackageInfo::dependencies` recursively.

The current fetch status per source kind (only git and directory
actually pull bytes today) lives in
[docs/packages.md](../../../docs/packages.md).

## Convenience helpers

[`cppup_config.hpp`](cppup_config.hpp) keeps the older flag-list
helpers around for terse `build.cpp` files:

```cpp
config.compile_flags = warnings::extra();            // -Wall -Wextra
config.compile_flags = warnings::pedantic();         // + -Wpedantic
config.compile_flags = optimization::aggressive();   // -O3 -flto
config.compile_flags = cpp_standard::cpp23();        // -std=c++23

config.profiles = {
    debug_profile({Flag{"-fsanitize=address"}}),
    release_profile({Flag{"-march=native"}}),
    test_profile("catch2", {Flag{"--coverage"}}),
};
```

These predate the `CxxStandard` / `WarningLevel` enums on `Toolchain`.
New code should prefer the enums (which adapt across compiler
families); the helpers are useful when you want to mix and match flag
sets without going through a `Toolchain`.

## Examples

### Library + tests

```cpp
extern "C" BuildConfiguration configure()
{
  BuildConfiguration config;

  config.toolchain                = Toolchain{"clang++"};
  config.toolchain->cxx_standard  = CxxStandard::Cxx23;
  config.toolchain->warnings      = WarningLevel::Strict;

  config.packages = {package_helpers::from_git(
      "fmt", "https://github.com/fmtlib/fmt.git", "10.2.1")};

  config.libraries = {
      Library{.name = "mylib", .sources = {"src/lib/*.cpp"}, .type = LibraryType::Static},
  };
  config.test_frameworks = {TestFramework{.name = "gtest"}};
  config.tests = {
      Test{.name = "unit", .sources = {"tests/*.cpp"}, .framework = "gtest"},
  };

  return config;
}
```

### Cross-platform binary with feature flags

```cpp
extern "C" BuildConfiguration configure()
{
  BuildConfiguration config{
      .toolchain = Toolchain{"g++"},
      .sources   = {"src/main.cpp"},
      .binaries  = {Binary{.name = "app", .sources = {"src/main.cpp"}}},
  };

  when_linux  ([&] { config.link_flags.push_back(Flag{"-pthread"}); });
  when_windows([&] { config.link_flags.push_back(Flag{"ws2_32.lib"}); });

  when_feature(config, "telemetry", [&] {
    config.packages.push_back(package_helpers::from_git(
        "otel", "https://github.com/open-telemetry/opentelemetry-cpp.git", "v1.16.1"));
    config.definitions.push_back(Definition{"TELEMETRY_ENABLED"});
  });

  when_env_exists(config, "CI", [&] {
    config.compile_flags.push_back(Flag{"-Werror"});
  });

  return config;
}
```

### Profile-aware

```cpp
extern "C" BuildConfiguration configure()
{
  BuildConfiguration config;
  config.binaries = {Binary{.name = "app", .sources = {"src/main.cpp"}}};

  config.profiles = {
      Profile{.name = "debug",   .compile_flags = {Flag{"-O0"}, Flag{"-g"}}},
      Profile{.name = "release", .compile_flags = {Flag{"-O3"}}, .definitions = {Definition{"NDEBUG"}}},
  };

  when_profile("release", [&] {
    config.compile_flags.push_back(Flag{"-flto"});
  });

  return config;
}
```

Select with either:

```bash
cppup build --profile release          # one-off
cppup profile select release           # persisted to cppup.lock
```

## How `configure()` is called

1. The CLI resolves *early* toolchain + profile from CLI flags,
   `cppup.lock`, and env (`$CXX` / `$CC`); exports them as
   `CPPUP_ACTIVE_TOOLCHAIN` / `CPPUP_ACTIVE_PROFILE`.
2. The CLI compiles `build.cpp` against the amalgamated
   `<cppup/configuration.hpp>` and links against nothing else
   (configuration is header-only at the user side).
3. The CLI `dlopen`s the resulting `.so`, looks up `configure`, and
   calls it. The inherited environment makes `when_toolchain` /
   `when_profile` produce the right branches.
4. The returned `BuildConfiguration` is passed through the toolchain
   expander, profile processor, build-step executor, and finally the
   buildsystem driver to compile and link the project.

This means: anything `configure()` does inside `when_toolchain` /
`when_profile` already sees the resolved selection. Anything outside
those guards runs unconditionally and is part of every build.

See also: [docs/packages.md](../../../docs/packages.md) (lockfile,
selection, sync) and [docs/plugin_api.md](../../../docs/plugin_api.md)
(extension ABI, test-framework integration).

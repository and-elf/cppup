# cppup package manifests

This directory is the design home for the cppup package-manifest format
(`package.toml`) — the TOML descriptor that a package registry serves to
clients and that local recipes/contributors author by hand. Think of it as
a declarative, TOML-only sibling of Conan's `conanfile.py`: no Python, no
methods, no logic — just data.

The repo is a **mono-repo** holding the registry index, every generated
manifest, and the tooling that produces them. Layout:

```
manifests/
├── README.md              ← this file (schema + rationale)
├── SCHEMA.md              ← field-by-field reference (TODO)
├── INDEX.md               ← registry-index format
├── index.yaml             ← machine-readable index (generated)
├── examples/              ← hand-written canonical examples (docs only)
│   ├── library-fmt.toml
│   ├── library-zlib.toml
│   ├── tool-ninja.toml
│   ├── toolchain-gcc-13.toml
│   └── plugin-ninja-builder.toml
├── recipes/               ← generated by conan2toml, never hand-edited
│   └── fmt/10.2.1/package.toml
└── tools/
    └── conan2toml/        ← Python tool: conanfile.py → package.toml
```

> **`examples/` vs `recipes/`** — `examples/` is a small, hand-written set
> kept *only* to document the schema and pin behavior in converter tests.
> `recipes/` is bulk machine output: every file there is regenerated from
> an upstream `conanfile.py` by `conan2toml`. Do not hand-edit `recipes/`.
> If a generated manifest is wrong, fix the converter (or upstream the
> patch into Conan Center) and regenerate.

## Design goals

1. **TOML-only.** Every recipe is pure data. No `def build(self):` hooks.
   If a build needs custom logic, it goes into a build-system plugin, not
   into the manifest. This is the wedge that distinguishes cppup from
   Conan: recipes are statically inspectable, diffable, and trivially
   re-hostable on any registry.
2. **Mirror the in-process model.** Field names and enums track the
   existing C++ types so parsing is a thin TOML → struct mapping:
   - `PackageInfo` ([src/core/configuration/types.hpp:49](src/core/configuration/types.hpp#L49))
   - `Toolchain` ([src/core/configuration/types.hpp:418](src/core/configuration/types.hpp#L418))
   - `DependencyRequirement` ([src/core/dependency/resolver.hpp:44](src/core/dependency/resolver.hpp#L44))
   - Plugin `Manifest` ([src/core/plugin/manifest.hpp:36](src/core/plugin/manifest.hpp#L36))
   - Lockfile `Entry` ([src/core/cli/commands/lockfile.hpp:52](src/core/cli/commands/lockfile.hpp#L52))
3. **Source-builds only, for now.** A manifest describes how to fetch and
   build a package from source. Pre-built binary support is out of scope
   for v1 but the schema reserves a `[binary]` table for later.
4. **One schema, four kinds.** A `kind` discriminator picks which optional
   sections are meaningful, but a parser can always read every file with
   the same code path.

## Top-level shape

```toml
schema  = 1                    # bumped on breaking change

[package]
name        = "fmt"
version     = "10.2.1"
kind        = "library"        # library | tool | toolchain | plugin
description = "A modern formatting library"
license     = "MIT"
homepage    = "https://fmt.dev"
repository  = "https://github.com/fmtlib/fmt"
cppup_compat = ">=0.5.0"       # required cppup version (semver constraint)

[source]
type       = "git"             # git | tar | zip | http | registry | directory
url        = "https://github.com/fmtlib/fmt.git"
tag        = "10.2.1"          # or git_branch / git_commit
subdirectory = ""              # optional path inside fetched tree
checksum   = "sha256:..."      # required for tar/zip/http

# Optional patches — referenced by URL (commit-pinned in the upstream
# index repo), never vendored. Fetched and sha256-verified by the client
# before being applied. Eliminates the need for a sibling patches/ dir
# and keeps every package.toml self-contained.
[[source.patches]]
url         = "https://raw.githubusercontent.com/conan-io/conan-center-index/<commit>/recipes/<pkg>/all/patches/<file>.patch"
sha256      = "..."
description = "Short reason this patch is applied"
strip       = 1                # -p<N> argument

[build]
system = "cmake"               # name of a registered build-system plugin
args   = ["-DFMT_TEST=OFF"]    # verbatim args to the build system

# Feature flags consumers can toggle. Each becomes an option propagated
# through dependency resolution and into the lockfile.
[features]
shared      = { default = false, description = "Build as shared library" }
header_only = { default = false, description = "Header-only mode" }

# Dependency scopes mirror DependencyRequirement.dependency_type.
# Constraint syntax: =, >=, <=, >, <, ~ (compatible), ^ (caret), || (or).
[dependencies]
# runtime — propagated to consumers
# (none for fmt)

[build-dependencies]
# build-time only — tools / generators
# cmake = "^3.15"

[test-dependencies]
# only pulled in when building this package's tests
# gtest = "^1.14"

# Platform gating; omitted = all supported.
[platforms]
os   = ["linux", "macos", "windows"]
arch = ["x86_64", "arm64"]
```

### Kind-specific sections

**`kind = "library"`** — uses `[source]` + `[build]`. Exposes consumers to
include dirs and link names via:

```toml
[[exports]]
type          = "library"      # library | header_only | binary
name          = "fmt"
include_paths = ["include"]
link_flags    = []
```

**`kind = "tool"`** — same `[source]` + `[build]`, but exports one or
more executables instead of libraries:

```toml
[[exports]]
type       = "binary"
name       = "ninja"
install_as = "ninja"
```

**`kind = "toolchain"`** — describes a compiler installation; mirrors
the `Toolchain` struct:

```toml
[toolchain]
cxx          = "g++-13"
cc           = "gcc-13"
cxx_standard = "c++20"         # c++17 | c++20 | c++23 | c++26
warnings     = "strict"        # none | standard | strict | werror
extra_flags  = ["-fno-rtti"]
```

The `[source]`/`[build]` blocks remain optional — a toolchain manifest
can either point at a buildable GCC source tree or simply describe an
already-installed compiler that the registry promises is available.

**`kind = "plugin"`** — mirrors `core/plugin/manifest.hpp`:

```toml
[plugin]
cppup_compat = ">=0.5.0"
build_hash   = ""              # filled by build, may be empty in source manifest
commit_hash  = ""

[[plugin.entries]]
id             = "ninja"
kind           = "build_system"  # build_system | package_source | logger | template | test_system
vtable_version = 1
description    = "Ninja build runner"

[plugin.dependencies]
system  = ["ninja"]
plugins = []
```

## Versioning & constraints

Constraint syntax matches `VersionConstraint`
([src/core/dependency/resolver.hpp:33](src/core/dependency/resolver.hpp#L33)):

| Syntax    | Meaning                  |
|-----------|--------------------------|
| `1.2.3`   | exact                    |
| `>=1.2.3` | greater or equal         |
| `<=1.2.3` | less or equal            |
| `>1.2.3`  | greater than             |
| `<1.2.3`  | less than                |
| `~1.2.3`  | compatible (`>=1.2.3, <1.3.0`) |
| `^1.2.3`  | caret (`>=1.2.3, <2.0.0`)      |

## Relationship to the lockfile

`package.toml` is the input; `cppup.lock` is the output. The lockfile
records the *resolved* version, source URL, commit, checksum, and
selected features for every package in the dependency tree — schema
already defined at [src/core/cli/commands/lockfile.hpp:27](src/core/cli/commands/lockfile.hpp#L27).
A manifest is hand-authored; the lockfile is machine-written.

## Why TOML, not Python

Conan's `conanfile.py` is expressive but pays for it:

- recipes can do anything → registry must execute untrusted code or sandbox it,
- diffs are noisy (logic + data + helpers in one file),
- non-Python clients (Rust, Go, C++ — cppup itself) have to re-parse Python,
- caching the result of a recipe means caching a Python execution.

A declarative TOML manifest moves all variability into well-typed
options/features and into build-system plugins, which are the right place
for behavior. The trade-off is that some Conan recipes won't translate
1:1 — those need a small plugin (or a `build.script` escape hatch we may
add later if pressure warrants it).

## conan → cppup migration

A tiny Python tool — `manifests/tools/conan2toml/` — will consume an
existing `conanfile.py`, instantiate the recipe with a mock Conan API,
and snapshot the resulting attributes (`name`, `version`, `requires`,
`options`, `settings`, `url`, `homepage`, `license`, `topics`) into a
`package.toml`. Method-based fields (`build()`, `package()`,
`package_info()`) are surfaced as TODOs in a comment block at the top of
the generated file so a human can map them to a build plugin invocation.

See `tools/conan2toml/README.md` (TODO) for the design.

## Open questions

See `tools/conan2toml/GAPS.md` for the full conversion-blocker list.
Schema-level items still under discussion:

- **Profiles.** Conan profiles map roughly to cppup's `Profile`
  ([src/core/configuration/profile.hpp:14](src/core/configuration/profile.hpp#L14)).
  Profiles are a consumer-side concept and probably don't belong in
  individual package manifests — they live in the workspace, not the
  registry.
- **Binary packages.** Reserve `[binary]` for cache descriptors but defer
  the actual schema until source-build resolution is solid.
